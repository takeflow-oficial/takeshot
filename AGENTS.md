# Takeshot agent guide

Takeshot is a screenshot tool written in Rust with egui: capture with PrtSc, annotate, and style the result with backgrounds and watermarks. The redesign in progress turns it into a tray utility with editable objects. Product context and principles: [PRODUCT.md](PRODUCT.md). Visual source of truth: [design/takeshot-ui.fig](design/takeshot-ui.fig) (open it in OpenPencil or Figma).

## Parity

Takeshot ships two themes, **TakeUI** and **Coral UI**, each with light, dark and system modes, over one layout. A theme changes the colours (`Tokens`), the brand mark and name (`ui::brand`) and the look of a few kit components (selection marks, the active tool, the switch knob, the slider line); it never moves a function. Parity means a visible change looks right in all four looks: TakeUI and Coral UI, light and dark. Use the `implementar-issue` skill for any change a user can see.

The pages of the design file and the rule that keeps it current are in [The design file](#the-design-file).

## The design file

[design/takeshot-ui.fig](design/takeshot-ui.fig) (OpenPencil or Figma) draws the app as it is today, screen by screen, and is the visual source of truth. It has four pages:

| Page | Holds |
|---|---|
| "Sistema de design" | the kit's components in each theme ("TakeUI · componentes", "Coral UI · componentes") and the behaviours decided so far ("Comportamento decidido") |
| "Telas · TakeUI" | every screen of the app at its real size, light and dark: the main window (Início as a grid, as a list and with the detail panel; Estilo; the five sections of Ajustes, with the scroll bar where the app scrolls), the editor, the capture, the copy notice, the pinned picture, the tray menu and the dialogs |
| "Telas · Coral UI" | the same screens in Coral UI |
| "Instalador" | the Windows installer and the macOS dmg window (their pictures come from `assets/brand/installer-*.svg` and `dmg-background.svg`) |

Keeping it current is part of every visible change, in the same pull request:

- A change that adds or alters what a screen shows (a row, a control, a string, a spacing, a state, a scroll bar) edits that screen's frames in both "Telas" pages, in the four looks. A new screen gets its frames in all four looks; a removed one loses them; a frame nothing shows any more is deleted.
- The app is the truth. Draw from its render (`--screenshot`, with `--page`), never from memory, and compare the finished frame with that render: a frame that disagrees with the app is a bug in the file.
- A visual with no precedent in the kit is drawn first on a dated page ("Proposta (AAAA-MM-DD)") and approved before the code. When the app ships it, its frames move to the "Telas" pages and the proposal page goes.
- A change that reaches the kit also updates the matching component frame in "Sistema de design".
- The frames draw the Windows and Linux window. A control the app shows only on macOS (the Dock row in Ajustes > General) stays out of them, and its check is in [docs/testing-macos.md](docs/testing-macos.md).

## Layout

| Folder | Holds |
|---|---|
| `src/main.rs` | entry point: arguments, shared state, window modes |
| `src/engine/` | drawing engine: annotations, objects, pointer policy, rendering, background presets |
| `src/system/` | operating system and data: screen capture and monitor work areas, clipboard and files, the captures folder and its thumbnails (`library`, with their disk cache in `thumbcache`), fonts, settings, desktop notifications (`notify`), and the resident's parts (`resident`, `headless`, `tray`, `hotkeys`, `prtsc_hook`, `instance`, `autostart`, `recents`, `borderless`) |
| `src/ui/` | design system: `assets` (embedded fonts and the icon font), `tokens` (colours per theme and mode), `i18n` (strings), `icon` (Lucide), `style` (egui visuals), `kit` (components), `brand` (icons, mark and the theme's wordmark), `chrome` (the theme's title bar: drag, double click, resize edges, window buttons, the native fallback), `gallery` (all of it on one screen) |
| `src/screens/` | window state and behaviour (`home`, `editor` and `overlay` hold the main window's, the editor's and the capture's state and carry out their `MainAction`s, `EditorAction`s and `CaptureAction`s; the editor's canvas is `Editor::canvas`), the pin window and the copy notice, and the resident's `shell` (main window, tray menu, About and close dialogs) |
| `src/views/` | how the screens draw, in both themes: the main window (`shell`, `home`, `style`, `settings`), the editor (bars, panel, object bar) and the capture's bars, from the state in `screens/`; they return what the user asked for as actions, which `screens/` carries out. `begin_frame` applies the look when it changes |
| `assets/` | embedded fonts with their licenses, and the brand SVG masters with the PNG, ICO and ICNS files generated from them |

Every `.rs` file starts with a `//!` doc comment (after any crate attributes) stating its responsibility; read those lines to find your way, and give every new file one. Behavior lives in `engine/` and `system/` so every window shares it.

## Interface rules

- Hover and press change color only; every widget keeps its size and position (egui `expansion` stays 0).
- The pointer shows what a click will do: arrow on bars and panels, crosshair only while drawing on the image, move over draggable objects and inside the capture area, resize on handles, text cursor while typing.
- Every user-facing string is a `Msg` key in `src/ui/i18n.rs` with English and Portuguese text; the exhaustive `match` turns a missing translation into a compile error. Show it with `t(Msg::…)`.
- Widgets come from `src/ui/kit.rs` and colours from `Tokens`; a new widget joins the kit with a size that never depends on hover, and the kit test covers it.
- Motion is limited to 80 ms color transitions and the 150 ms "Copied" notice.
- All code, assets and values are original work or come from openly licensed sources listed in [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md).

## Objects on the picture

Editor and capture share one behaviour:

- Annotations are objects in `engine::doc::Doc`: ids, selection, transforms and an undo history of snapshots. A whole drag is one undo step (call `begin_change` once, then `translate_selected` or `resize` per frame). Selecting never changes `revision`, which is how the editor knows there is nothing to save.
- Screens route the pointer and keys through `Annotator::handle_canvas`, `handle_object_keys` and `handle_history_keys`, and set the pointer over the picture from `engine::cursor::pick` instead of picking icons by hand.
- Any tool moves the object under the pointer: `Doc::hit` is the object itself (an outline's line, a filled shape, a text), never its box, and `engine::cursor::pick` shows the move cross there; off every object the tool draws. The Text tool edits a text it clicks (the caret goes where it was clicked); a double click edits a text with any tool.
- The text being typed is an egui `TextEdit` placed over the picture by `Annotator::handle_typing`, in the text's font and size: Enter keeps it, Shift+Enter starts a line, Esc keeps it and leaves; its dashed frame moves it. Text is sized by the em in the picture too (`fonts::px_scale`), so it never jumps between live drawing and the final image.
- The wheel: a plain notch changes the width (or the text size) by one step (`wheel_notches` reads the events: egui smooths the wheel over frames); Ctrl+wheel and the pinch zoom the editor in proportion around the pointer, and the preview is rendered again 150 ms after the zoom rests, within the GPU's texture side.
- A slider drag is one undo step too: a view sends `Gesture(true)` when it is grabbed and `Gesture(false)` when let go (`Doc::begin_gesture`, `end_gesture`); a frame with no button down closes one left open. Restyles go through `Doc::restyle_selected(&Restyle)`, whose colour and opacity are apart, so a multi-selection keeps each object's other half. Picking from a list goes through `Annotator::pick`, which copies the object's style into the options, as a click on the canvas does.
- Each frame: `bake()` first (it returns annotations to render only when the picture is out of date), then the pointer, then `paint_selection`. During a drag only its start re-bakes, to take the dragged objects out, and `paint_selection` paints `painted_live()` until the drop re-bakes. A big capture never re-renders while a drag moves something; arrow nudges and Ctrl+D re-render once per press.

## The capture's bars

`engine::placement::capture_bars` places them, tested on its own: the tools in one column beside the area (right, else left) from its top, past its bottom only when the area is lower; the options panel next to them; the actions in a row under the area (over it without room) ending at its right edge. The tools' side depends on their own width alone, so they stay put while the options come and go; the options go beside them away from the area, else on the area's other side, and only with no room left do they cover the area. The view hands it the frames' drawn sizes from the frame before.

The bars also keep off the selected object or the text being typed (`Overlay::bars_avoid`: the selection's bounds, or `Annotator::draft_on_screen`, with the handles' reach), which matters when the area is the whole screen and the bars sit over it: a part whose place covers the object moves, one with no clear place stays where it was (an object filling the screen's edge), and with the object out of the way every place is the one above. The tools take the opposite end of their edge (the screen's bottom), then the screen's top, then the other side, by the object alone, so the options still never move them; the options drop `GAP` under the object in their column, else rise `GAP` over it; the actions take, after their own place, right under it or right over it (ending where it ends), then their other places, the first that is clear of it. The bars hide while a shape is drawn, an object dragged or a text moved by its dashed frame (`Annotator::busy`, which typing alone does not set) and come back when it is let go.
With Settings > Capture > "Area capture on every screen" (off by default, hidden on Wayland, where a window gets no position) the capture has one `Overlay` per monitor: `capture::grab_all` grabs them (the one under the mouse first, the others best-effort), `Mode::Overlay` shows the first in the root window and the others in immediate viewports (`capture_viewport`), and `overlay::settle` keeps a single area: the window that gains one makes the others drop theirs and their marks (`clear_area`). What ends the capture happens on the area's monitor: `active_shot` and `place_for` put the editor and the notice there, and the save dialog is owned by the first window, because the others have no `eframe::Frame` and a dialog without an owner opens behind these always-on-top windows.

## The resident

`takeshot` with no arguments starts the resident: one process per user owns the tray icon, the global hotkeys and the main window, and a second launch only shows it. Captures, editors and pinned images run as their own processes (`--capture`, `--edit`, `--pin`).

- Event sources (hotkeys, the PrtSc hook, the tray, a second launch) only send a `ResidentEvent` and request a repaint; `App::logic` drains them, so they act while no window is shown. On Windows and macOS the root viewport is an invisible host and the main window a child viewport. On Linux the root is the main window, and Wayland cannot hide a window: `run_resident_windows` (`main.rs`) makes the main window when `Shell::wants_window` and destroys it to hide it to the tray (`Shell::hide` closes it, and `leaving` keeps that close from being asked about again); between windows `system::headless` runs one egui pass per wake-up on a context nobody sees, and the senders of `ResidentEvent`s are retargeted (`Resident::retarget`) to the window that exists. A window made again carries a fresh `Home` (its textures belong to its context), opened on the page `Shell::take_page` holds. On Wayland a Show for a window that is not in front replaces it, since a client cannot focus itself. The window is only destroyed while a panel shows the tray icon (`Resident::tray_shown`: a StatusNotifier host is registered on the session bus, `tray::shown`); with none (stock GNOME) the X only minimizes it, and a hidden start (`--minimized`) waits `headless::TRAY_WAIT` (30 s) for a panel before showing the window, so the app is never left with no way back.
- The copy and save notice is a window in the theme's look, except on Wayland, where a client gets neither a position nor always-on-top and the capture window is full screen: there `system::notify` shows it as a desktop notification (a click on a saved capture opens its folder) and the capture window closes at once.
- A capture whose selection is on screen holds `instance::CaptureSlot`; another `--capture` exits before grabbing the screen.
- The warm capture (`system::standby`, Windows only for now): the resident keeps one `takeshot --capture-standby` process, a window and GL context that exist already, 1 by 1, transparent, click-through, off screen, off the taskbar and not active (`invisible_host`; not hidden, because eframe wakes an invisible window only every 100 ms; not active, because the next standby boots while a capture is on screen and an active window would take its keyboard, Esc and Enter included). It saves the ~200 ms a `--capture` process spends making them: PrtSc from the tray goes from ~320 ms to ~105 ms (median, injected PrtSc to the capture window on screen), and from ~620 to ~420 ms with the main window open, which still waits the 0.3 s for it to leave the picture. `actions::start_capture` (the hotkeys, the tray and the main window's buttons) sends `capture area <delay_ms>` on `<endpoint>-standby` for area captures only; `--full`, the 3-second capture and Wayland start `--capture` as before. The standby takes the `CaptureSlot` and answers `ok` (`busy` when a capture is on screen, and that PrtSc is ignored), then `App::activate` reloads the settings (look, language and options may have changed), grabs the screen and turns the window into the capture window with viewport commands (`capture_window_commands`, kept equal to `capture_viewport` by a test) and keeps it off the taskbar, as `capture_viewport` does for a `--capture` process (a button while the screen is being picked is what other screenshot tools do not show; `switch_to_editor` puts the editor on the taskbar with `show_in_taskbar`, and the notice stays off it); from there it is the editor or the notice like any capture. It serves one capture and closes its socket, so a later PrtSc never reaches a process that is already the editor. `Keeper` decides when the next one starts: `RESPAWN_AFTER` (1.5 s, off the first frames of the capture) after one was used, never twice within `WARM_UP` (10 s) while one is still booting; with no answer in 250 ms the capture falls back to a `--capture` process, so the feature can only make PrtSc as slow as before. A standby registers as a child like the others (the tray's Quit closes it) and leaves by itself after about 5 s when the resident is gone. It idles at 0 % CPU and about 71 MB of working set (90 MB private, the resident's own is 74 and 91). `TAKESHOT_NO_STANDBY=1` switches it off, and `TAKESHOT_STANDBY_LOG=<file>` appends the milliseconds of each step of a warm capture. Its fonts are those of when it started, so a font installed meanwhile shows from the next standby on.
- Editors, pinned pictures and the capture register with the resident (`instance::register_child`) and listen on a socket of their own (`listen_for_quit`). The tray's Quit goes in two steps (`QuitRun`): it asks each whether it may close (an editor with unsaved edits asks its user), and only once all have answered tells them to close, or to stay when one cancelled, so one Cancel keeps everything open, the resident included. A child answers in `App::logic`, which runs while its window is minimized or hidden.
- A borderless, rounded, transparent window on Windows needs `borderless::flatten_borderless`: egui-winit always asks winit for the undecorated shadow, which shows as a 1 px line across the top and a square shadow around the corners.

## Verify before calling work done

1. `cargo fmt --check` prints nothing.
2. `cargo clippy --all-targets -- -D warnings` finishes with zero warnings, pre-existing ones included.
3. `mkdir -p shots` once (the folder is git-ignored), then `cargo test > shots/test.log 2>&1` and read the log. Send test output to a file and run one test command at a time: a pipe holds a hung run open.
4. For visible changes, render the screens and compare them with the design file: the pictures of the screens are the `.fig`'s own frames (OpenPencil's `export_image` shows one), and the exact measures (sizes, padding, gaps, font sizes) are on its nodes, read through OpenPencil. A visible change ends with the `.fig` updated (see [The design file](#the-design-file)). Screenshots of Início use `--captures-dir docs/images` (the README's pictures) as sample captures, never the user's own folder. `--screenshot out.png` saves the window after ~120 frames and works with every window: `takeshot --screenshot out.png` (main window), `takeshot --edit --screenshot out.png` (editor with a sample picture), `takeshot --capture --screenshot out.png` (capture overlay on a sample). `takeshot` alone starts the resident (close a running one first); debug builds are console programs, so a script that launches one must redirect its output or the new console window takes the focus. `--lang en|pt|auto`, `--theme takeui|coral` and `--mode light|dark|system` override the saved look for this run in every window drawn from the tokens; `--page inicio|estilo|ajustes` opens the main window on that page (`--section geral|captura|salvar|atalhos|sobre` opens Ajustes on that section), `--page editor` the editor and `--page captura` the capture (both on the sample picture, the capture with an area and a mark), `--page aviso` the copy notice, and `--page componentes` the component gallery; `--captures-dir <folder>` shows another folder in Início and `--select <file name>` starts it with that capture chosen (its detail panel filled). None of them touches the saved settings. Screenshots for the repo or a PR use a sample folder, never the user's own captures. `scripts/screenshots.sh` renders the gallery, the three pages, the editor, the capture and the notice in Portuguese in all four theme/mode combinations into `shots/`, with `docs/images` as Início's captures (build with `cargo build --release` first).
5. Before a push, `scripts/check.sh` runs what CI runs: fmt, clippy and tests here, then the same on Linux in a container (`scripts/ci-linux`, needs Docker) plus clippy for macOS, on the commit being pushed. Code behind `#[cfg(...)]` for another system compiles only there, so steps 1 to 3 on Windows miss it. The pre-push hook runs it once a clone has `git config core.hooksPath .githooks`.

## Tools

- `scripts/dev.sh [takeshot arguments]`: live preview. Rebuilds into `target/dev-watch` and reopens the window whenever `src/`, `assets/` or `Cargo.toml` change (default `--page componentes`).
- Installers: `cargo-packager` 0.11.8 (`cargo install cargo-packager --version 0.11.8 --locked`) reads `[package.metadata.packager]` in `Cargo.toml`. On Windows, `cargo build --release` then `cargo packager --release --formats nsis,wix`; the NSIS template is `packaging/windows/installer.nsi` (cargo-packager's, with Takeshot's changes marked: it runs without an administrator, asks who to install for, just me under `%LOCALAPPDATA%\Programs` or every user, relaunching itself elevated only then, and the uninstaller removes the login entry). Its icon is `assets/brand/takeshot.ico` and its pictures `packaging/windows/installer-*.bmp`, rendered by `cargo run --example brand`. `scripts/linux-packages.sh` builds the deb, AppImage and tar.gz in the CI image and prints the libraries the binary needs; `scripts/linux-smoke.sh` opens them in clean Ubuntu containers (X11 and Wayland), saves what they drew, and checks that the resident's window comes and goes (`scripts/container/resident-check.sh`). `docs/testing-macos.md` is the manual check for the Mac.
- `scripts/release-local.sh vX.Y.Z [--dry-run] [--no-macos]`: the files of a release, built here and uploaded to its draft release (the flow is under [Git](#git)). It needs Docker running, 7-Zip, `gh` signed in and `cargo-packager` 0.11.8. `--dry-run` builds into `dist/<version>/` and lists what would go up, with no call to GitHub and nothing created there; `--skip-check` (dry run only) leaves out `scripts/check.sh`. `.github/workflows/release-macos.yml` is its macOS half: `workflow_dispatch` with the tag, it builds only the macOS target of `build.yml` (`targets`, `ref` and `checks: false` are `build.yml`'s inputs for it) from the commit the release points to, and attaches the dmg to the release, draft or not.
- `scripts/release-sums.sh vX.Y.Z [--dry-run]`: downloads the installers a release holds (draft or published), writes their `SHA256SUMS` and uploads it as one more file, so a download can be checked. It refuses a release that does not hold exactly the names `build.yml` gives (the dmg is the last to arrive), and compares the files in `dist/<version>/` with what the release holds. Run it again when a file of the release changes (a dmg built again).
- `cargo run --example brand`: renders `assets/brand/*.svg` into the PNGs, `takeshot.ico` and `Takeshot.icns`, and `takeshot-banner.svg` into `png/takeshot-banner.png` (1280 x 640, the README header and GitHub's social preview, which only the repository's Settings can set). Run it after changing an SVG and commit the outputs; `build.rs` embeds `takeshot.ico` in the Windows executable.

## Skills

`.claude/skills/` holds the procedures for agents: `implementar-issue` takes an issue or a request to an open PR (any change a user can see included, in both themes, with the design file updated), and `revisar-pr` reviews a pull request by running it (build, tests, the binary on Windows and in Linux containers) and checks that the design file follows the screens it changes.

## Git

- Branch `feat/<topic>` or `fix/<topic>` from `main`, open a PR to `main` and fill in the template.
- Commit messages: English, [Conventional Commits](https://www.conventionalcommits.org/).
- CI (`.github/workflows/ci.yml`) runs fmt, clippy and the tests on Windows, macOS and Linux for every pull request, and builds the seven installers as artifacts when the pull request touches how they are made (`Cargo.toml`, `Cargo.lock`, `build.rs`, `packaging/`, `assets/brand/`, `.github/`); `ci.yml`, `release.yml` and `release-macos.yml` all call `.github/workflows/build.yml`.
- A release is made on the maintainer's PC: bump `version` in `Cargo.toml` in a pull request, merge it, then run `scripts/release-local.sh vX.Y.Z` on a clean checkout of `main` (`--dry-run` first to see the files). It runs `scripts/check.sh`, creates the GitHub Release as a draft pointing at that commit, starts the `release-macos` workflow (the dmg builds on GitHub in parallel), builds the Windows files (setup.exe, msi, portable zip) and the Linux ones (deb, AppImage, tar.gz) and uploads them with `--clobber`. The names are `build.yml`'s, which the script compares with its own list. It refuses a version that is out already and a repository that signs on CI (`SIGN_WINDOWS`), since the script does not sign. Once the dmg is attached, `scripts/release-sums.sh vX.Y.Z` puts the `SHA256SUMS` of the seven files on the release (the README tells downloaders how to check one). It never publishes: a maintainer publishes the draft with `gh release edit vX.Y.Z --draft=false`, which creates the tag `vX.Y.Z` on the draft's commit. No tag is pushed by hand.
- The `release` workflow (Actions > release > Run workflow on `main`, or `gh workflow run release`) does the same release on GitHub's runners: lint, tests and the seven installers on the three systems, then the tag and the published release, with its `SHA256SUMS`. It takes some 45 minutes (the macOS runner queues), so it is the fallback for when this PC cannot build; use one path per version. It keeps its lint and tests on purpose: `ci.yml` runs on pull requests only, so the merge commit on `main` is otherwise never linted or tested before it ships.
